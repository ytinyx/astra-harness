## 完成一项增量需要什么

一项增量应同时具备明确的行为、可演示入口、相称的验证与文档，不以新增类名或更多通过数量代替交付。

1. 用实际任务说明输入、输出和边界；把取消、失败、超限的结果先定义清楚。
2. 增量沿现有执行主线实现，新增工具继续走 Registry／Executor，不从界面绕过审批。
3. 核对实际产物和副作用，必要时注入失败；区分“安全停止”和“任务完成”。
4. 更新对应指南与交接记录，验证安装入口、文档链接及涉及的界面流程。
5. 记录真正执行的检查与未执行项；涉及外部服务、费用或发布时按具体授权办理。

开发方法见 [贡献指南](../CONTRIBUTING.md)，技术取舍见 [设计决策](DECISIONS.md)。路线图本身不授权外部操作。

## 下一阶段的两项决定

### 当前组合的真实模型验证

当前全部工具与可选配置的真实模型表现需要单独验收；原项目某一传输版本的有限联调不能代表当前组合。开展时应固定模型、任务、提示、工具身份和预算，用独立产物判据验证选择工具、处理拒绝／错误和完成任务的能力。

Embedding 的本地 mock 用于检查协议、持久化与排序路径，不能证明真实服务的语义质量。验证新的模型或 Embedding 服务前，需要明确服务、合成材料、调用费用上限和停止条件。

### 公开交付方式

0.4.0 源码已采用 [MIT License](../LICENSE) 公开至 [ytinyx/astra-harness](https://github.com/ytinyx/astra-harness)，独立 Git 历史不继承原项目提交或内部阶段标签。首轮 CI 暴露的平台测试假设已修正；后续 CI 仍按对应提交核实，记录见 [当前交接](../HANDOFF.md)。GitHub Release 与 PyPI 安装包尚未发布，须分别安排构建与验证。

## 后续候选，需要问题驱动

以下是可以评估的方向，不是当前交付承诺，也没有据此创建空模块：

| 触发条件 | 可考虑的增量 | 验收重点 |
| --- | --- | --- |
| 代表性任务表明字符预算过粗 | 改进上下文度量和保留策略 | 保留当前工具配对；比较输入量、费用与完成情况 |
| 确有远程 MCP 服务需求 | 评估官方 SDK、认证与端点安全 | 凭据边界、断连与未知写操作不重放 |
| 用户操作出现可复现阻碍 | 针对具体界面流程优化 | 错误、取消、重复点击、重开与可访问性 |
| 需要解释机制带来的差异 | 更严格的实验对照 | 明确只改变什么；保留原始重复、失败和 unknown |

多 Agent、分布式 Worker、消息队列、长期记忆和完整前端框架迁移没有当前必要性证明。先以现有主线的真实使用结果决定是否增加复杂度。

## 历史阶段的阅读入口

下面按学习顺序介绍已实现的能力。各来源阶段的变化见 [版本说明](VERSION_TIMELINE.md)，当前环境的结果应重新运行相应入口核对。

### 阶段一：最小执行闭环

从固定模型与真实加法工具开始，理解 `ModelRequest → ToolCall → ToolExecutor → ToolResult → ModelResponse`。两轮模型阶段、一次加法调用只是这个特定示例的行为，不是所有任务的通用次数。教材见 [第一课](LESSON01.md)，执行实现见 [Engine](../astra_harness/engine.py)。

### 文件片段读取：已交付

`files.read_range` 已支持行列游标与固定返回量，并保留原 `files.read` 接口。整文件大小、路径保护、调用预算与旧运行快照仍检查。它控制进入上下文的内容，不承诺更少磁盘扫描；接口见 [文件片段读取](ARCHITECTURE.md#文件片段读取)，复现方法见 [片段对照](EVALUATION.md#文件片段与上下文对照)。

### 跨工具集评测身份：已交付

benchmark 保存工具契约与声明实现身份，条件不匹配时拒绝比较，不回填旧报告未记录的内容。工具提示文字变化单独提示；相同摘要不能证明整个环境或远端模型一致。规则见 [评测工具身份](ARCHITECTURE.md#评测工具身份)，示例见 [比较准入](EVALUATION.md#离线验证比较准入)。
