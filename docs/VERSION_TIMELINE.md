## 软件版本

| 软件版本 | 对应源码范围 | 如何理解 |
| --- | --- | --- |
| `0.2.0` | S01 | 基础运行框架的版本快照。 |
| `0.3.0` | S02 | 在前版基础上完善文件任务、流式展示与本地工作台。 |
| `0.4.0` | S03 起至当前开发线 | S03 引入持久暂停与配置化预算；后续增量仍沿用这一包版本。 |

本副本的 [pyproject.toml](../pyproject.toml) 与 [uv.lock](../uv.lock) 均声明包版本 **0.4.0**。“当前 0.4.0”汇总这条开发线的已有能力，不代表本副本是新建的正式发行。

原项目的旧 `v0.4.0` 标签只定位 S03，**不包含当前功能全集**。FastAPI、异步模型 I/O、多 MCP 服务、知识检索、可选 Embedding、工作区切换和配置档案等均为后续增量。

## 来源范围与内部索引

**本仓库不继承原项目 Git 历史，初始提交从本次公开整理开始。** 来源标记 S27 指原项目本轮工作区的图文整理，不是本仓库已有的标签。这里不能检出原项目的早期提交，也不能将 S27 称作原项目已建标签的版本快照。

`S01`—`S27` 只作内部演进索引。原项目保留 S01—S26 的 `stage/序号-主题` 标签及已有 `v0.2.0`、`v0.3.0`、`v0.4.0`、`v0.4.0-*` 兼容入口；这些旧标签没有导入本仓库。网页页脚的 `0.4` 是系列标识，不用于区分各增量。

原项目索引依据保存的源码快照重建，逻辑顺序不证明对应时刻已开发、测试或发布。独立公开历史不重造原项目历史，也不将缺少原始源码的早期设想补成已完成版本。

## 如何验证当前副本

以 [副本验证状态](../HANDOFF.md) 区分实际完成与未执行项。需要复现运行行为时，按 [评测协议](EVALUATION.md) 在当前环境重新生成报告，记录模型、输入、工具身份、预算、实际结果和源码散列。不能将新执行结果回填为早期版本的历史验收。

后续若分发不同构建，应明确发行版本并记录变化；内部索引不能解决同版本安装包的缓存和区分问题。路线图中的方向不会自动产生新版本、付费调用或发布授权。
